1. Паралелізм і потоки в C++

Паралелізм — це одночасне (або квазіодночасне) виконання кількох завдань однією системою. У сучасних ОС паралельність забезпечують процеси та потоки (threads): кожен процес має власний простір пам'яті, а потоки всередині процесу ділять пам'ять і ресурси.

У C++ для роботи з потоками використовується заголовок <thread>. Клас std::thread запускає функцію в окремому потоці виконання. 

#include <iostream>
#include <thread>

void hello() {
    std::cout << "Hello parallel world\n";
}

int main() {
    std::thread t(hello);
    t.join();  // головний потік чекає завершення t
}

Після створення потік потрібно або приєднати (join()) — дочекатися його завершення, або від'єднати (detach()) — дозволити йому працювати незалежно від життєвого циклу об'єкта std::thread у main. Якщо потік лишається «приєднувальним» (joinable) і знищується без join чи detach, викликається std::terminate().

2. Проблеми синхронізації доступу до даних

Коли кілька потоків одночасно звертаються до спільних даних (глобальний масив, список, поля об'єкта), виникають гонки даних (data races): результат залежить від порядку виконання операцій, який непередбачуваний.

  • Один потік читає структуру, інший її змінює — можливі хибні результати або пошкодження структури.
  • Навіть прості операції «читання + запис» у двох потоках без координації не гарантують коректності.
  • Для контейнерів STL (наприклад, std::list) одночасна модифікація та обхід без синхронізації можуть призвести до невизначеної поведінки програми.

Потрібен механізм взаємного виключення: у заданий момент лише один потік виконує критичну ділянку коду, що працює зі спільним ресурсом.

3. М'ютекс (mutex)

М'ютекс (від mutual exclusion) — примітив синхронізації. Потік перед доступом до спільних даних захоплює м'ютекс; інші потоки, що намагаються захопити той самий м'ютекс, блокуються, доки він не буде звільнений.

У C++: заголовок <mutex>, тип std::mutex.

  • lock() — захопити м'ютекс (очікування, якщо зайнятий);
  • unlock() — звільнити м'ютекс.
#include <mutex>

std::mutex m1;
int a[2] = { 2, 3 };

void thread1() {
    m1.lock();
    a[0] = a[0] + a[1];
    m1.unlock();
}

void thread2() {
    m1.lock();
    a[1] = a[0] * a[1];
    m1.unlock();
}

Поки один потік утримує m1, інший не змінить масив «посередині» операції — забезпечується інваріантний доступ до захищених даних у межах пар lock/unlock.

Увага. Викликати lock() і unlock() вручну не рекомендується: при винятку або ранньому return можна «забути» unlock(), що призведе до постійного блокування інших потоків.

4. std::lock_guard та RAII

Ідіома RAII (Resource Acquisition Is Initialization): ресурс (тут — блокування м'ютекса) захоплюється в конструкторі об'єкта-обгортки і автоматично звільняється в деструкторі.

Шаблон std::lock_guard<std::mutex> у конструкторі викликає lock(), у деструкторі — unlock().

void safe_update() {
    std::lock_guard<std::mutex> guard(m1);
    a[0] = a[0] + a[1];
    // unlock() викликається автоматично при виході з функції
}

Параметр std::adopt_lock

Якщо м'ютекс уже захоплено (наприклад, функцією std::lock), у конструктор lock_guard передають std::adopt_lock: обгортка лише приймає володіння існуючим блокуванням і звільнить м'ютекс у деструкторі, не викликаючи повторного lock(). 

std::lock(mtx_a, mtx_b);
std::lock_guard<std::mutex> ga(mtx_a, std::adopt_lock);
std::lock_guard<std::mutex> gb(mtx_b, std::adopt_lock);

5. Інкапсуляція: дані і м'ютекс в одному класі

Замість глобальних змінних і окремого глобального м'ютекса доцільно помістити захищені дані і м'ютекс у приватні поля одного класу. Так явно показується зв'язок між ресурсом і механізмом синхронізації; доступ до даних відбувається через методи класу з коректним блокуванням.

6. Взаємне блокування (deadlock) і std::lock

Якщо для операції потрібно два м'ютекси, а потоки захоплюють їх у різному порядку, можлива ситуація взаємного очікування:

  • Потік A захопив mtx1 і чекає mtx2;
  • Потік B захопив mtx2 і чекає mtx1;
  • Жоден не може продовжити — deadlock.

Функція std::lock(mtx1, mtx2, ...) атомарно захоплює кілька м'ютексів алгоритмом, що уникає взаємного блокування при одночасному захопленні в одній точці коду.

std::lock не усуває deadlock, якщо в різних місцях програми м'ютекси беруться по черзі в різному порядку без узгодженої дисципліни. Тоді залишаються узгоджений глобальний порядок захоплення або рефакторинг архітектури.

Обмін даними двох об'єктів exchangePerson у методі Swap потребує блокування двох м'ютексів — типовий випадок застосування std::lock разом із lock_guard і std::adopt_lock.

7. std::unique_lock

std::unique_lock — гнучкіша обгортка над м'ютексом, ніж lock_guard:

  • можна відкласти захоплення через std::defer_lock і заблокувати пізніше (lock() на обгортці або std::lock(lock1, lock2));
  • можна тимчасово звільнити м'ютекс (unlock()) і знову захопити;
  • підтримує переміщення володіння між об'єктами unique_lock.

Плата за гнучкість — більший розмір об'єкта та дещо вищі накладні витрати порівняно з lock_guard. 

std::unique_lock<std::mutex> la(a.mtx, std::defer_lock);
std::unique_lock<std::mutex> lb(b.mtx, std::defer_lock);
std::lock(la, lb);
// обмін даними; при знищенні la, lb — автоматичне unlock

У пункті 1.2.7 метод Swap реалізують через unique_lock і defer_lock замість пари std::lock + lock_guard(adopt_lock) з пункту 1.2.6 — логіка та сама, змінюється лише спосіб керування блокуванням.

8. join і detach: вплив на спостережувану поведінку

Операція Поведінка
join() Головний потік чекає завершення дочірнього; гарантовано можна покластися на результат роботи потока до продовження main.
detach() Потік працює у фоні; main може завершитися раніше — вивід у консоль може не встигнути з'явитися, процес завершується разом із потоками ОС.
Ні join, ні detach При знищенні joinable std::thread — std::terminate().
Для лабораторних дослідів пунктів 1.2.1–1.2.2 важливо кілька разів запустити програму й зафіксувати різницю виводу та завершення. Для коректної синхронізації з обміном даними (1.2.6) потік Swap зазвичай join(), щоб головний потік отримав результат до завершення програми.

9. Зв'язок теорії з практичними пунктами 1.2.1–1.2.8

1.2.1 — потоки без join/detach

Демонстрація правил життєвого циклу std::thread і недетермінованості при завершенні main.

1.2.2 — detach

Потоки від'єднані; відсутність terminate, але немає гарантії виконання до кінця main.

1.2.3 — список без м'ютекса

Потоки AddToList і ListContains працюють з глобальним std::list. Без синхронізації — гонки, частково заповнений список при перевірках, ризик UB при одночасній модифікації та обході.

1.2.4 — м'ютекс lock/unlock

Критичні ділянки обгорнуті в lock() / unlock(); структура списку залишається цілісною.

1.2.5 — lock_guard і багато коротких потоків

Одна операція додавання / одна перевірка на виклик; у main — цикл із 10 запусків і detach; RAII через lock_guard замість ручного unlock.

1.2.6 — класи, std::lock, adopt_lock

lock_guard у JohnDoe / JacobSmith; у Swap — перевірка &a != &b, std::lock, потім lock_guard з adopt_lock.

1.2.7 — unique_lock і defer_lock

Альтернативна реалізація Swap з відкладеним захопленням і std::lock(unique_lock, ...).

1.2.8 — висновки

Порівняння підходів до синхронізації:

  • один м'ютекс на ресурс — просто, але серіалізує доступ;
  • std::lock — для одночасного захоплення кількох м'ютексів;
  • lock_guard — мінімальні накладні витрати, фіксована область блокування;
  • unique_lock — коли потрібна відкладена блокування або складніше керування;
  • join / detach — про коректність завершення та видимість результатів, а не про deadlock як такий.

10. Коротке резюме

Паралельні обчислення в C++ базуються на std::thread. Спільні дані вимагають синхронізації; базовий інструмент — std::mutex. Надійніший стиль — RAII через lock_guard або unique_lock. При роботі з кількома м'ютексами застосовують std::lock і узгоджений порядок захоплення. Дані разом із м'ютексом доцільно інкапсулювати в клас. Практичні пункти лабораторної послідовно показують відсутність синхронізації, ручні м'ютекси, RAII, багатопотокову роботу зі списком та безпечний обмін між об'єктами з двома м'ютексами.
