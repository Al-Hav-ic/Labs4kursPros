# План реалізації лабораторної роботи №1

**Тема:** застосування м’ютексів та шаблонів стандартної бібліотеки для ізолювання доступу до даних у паралельних обчисленнях.

**Мова:** C++11 або новіше (`<thread>`, `<mutex>`, `<list>`).

**Середовище:** Windows (у методичці згадується `Windows.h` / `Sleep`; для очікування потоків краще `std::this_thread::sleep_for` або `join()`).

## 3. Покрокова реалізація

### 3.1 Пункт 1.2.1 — два потоки без join/detach

**Мета:** показати, що `main` може завершитися до виконання потоків.

**Реалізація:**

- Функції `Thread1()` → вивести `1`, `Thread2()` → вивести `2`.
- У `main`: `std::thread t1(Thread1); std::thread t2(Thread2);` — **без** `join()` і **без** `detach()`.
- Завершити `main` (наприклад, `return 0`).

**Очікувана поведінка при аналізі:**

- При завершенні `main` деструктори `std::thread` для ще «joinable» потоків викликають `std::terminate()` (програма може аварійно завершитися).
- Навіть якщо вивід з’явиться, результат **недетермінований** між запусками.

**Що записати в звіт:** 3–5 запусків, що саме вивелось / чи була помилка / чому так (життєвий цикл потоків vs `main`).

---

### 3.2 Пункт 1.2.2 — той самий код + `detach()`

**Зміни:**

- Після створення: `t1.detach(); t2.detach();`
- `main` одразу завершується.

**Очікувана поведінка:**

- Немає `terminate` через joinable thread.
- Вивід **може відсутні** або бути обрізаним — ОС може завершити процес до того, як потоки встигнуть вивести текст.
- Між запусками: інколи `1` і `2`, інколи нічого, порядок рядків може змінюватися.

**Висновок для звіту:** `detach()` не гарантує виконання до кінця `main`; для надійного результату потрібен `join()` або синхронізація (бар’єр, умова завершення).

---

### 3.3 Пункт 1.2.3 — `AddToList` і `ListContains` без синхронізації

**Дані:**

- Глобальний `std::list<int> l`.
- У `main` задати базове значення `int base` (наприклад, з `cin` або константа `100`).

**Потік `AddToList`:**

1. Додати `base` в кінець списку → повідомлення в консоль.
2. Ще 9 разів: додати значення на 1 більше попереднього доданого → після кожного додавання — повідомлення.
3. Разом 10 додавань: `base, base+1, …, base+9`.

**Потік `ListContains`:**

- 10 разів перевірити, чи є в `l` значення `base` (те саме, що в `main`).
- Кожну спробу вивести: «входить» / «не входить».

**Запуск:** два потоки одночасно; варіанти — обидва `detach` + `Sleep`/sleep у `main`, або один `join` обох після старту (методичка для 1.2.3 не вимагає `lock_guard`).

**Очікувані гонки (для висновків):**

- `ListContains` може бачити список **частково заповненим** → частина перевірок «не входить», потім «входить».
- Ітерація по списку під час одночасної модифікації → **невизначена поведінка** (UB) без м’ютекса; у звіті зазначити ризик пошкодження структури даних, не лише «логічні» гонки.

**Записати:** кілька запусків, таблиця «спроба 1..10 → результат».

---

### 3.4 Пункт 1.2.4 — той самий сценарій + м’ютекс

**Зміни:**

- Глобальний `std::mutex mtx`.
- У `AddToList`: перед роботою з `l` — `mtx.lock()`, після — `mtx.unlock()` (мінімально — на всю функцію або на кожну операцію додавання окремо).
- У `ListContains`: те саме навколо перевірки/обходу списку.

**Очікуваний результат:**

- Список завжди узгоджений під час перевірки.
- Після того як `base` додано, усі подальші перевірки мають давати «входить» (якщо `ListContains` ще виконується після повного додавання — завжди «входить»; якщо перевірки розподілені в часі — спочатку «не входить», після додавання `base` — «входить», але **без** пошкодження списку).

**Висновок:** м’ютекс забезпечує інваріантність структури та атомарність «ділянок» коду, але **не** фіксує порядок між потоками без додаткової логіки.

---

### 3.5 Пункт 1.2.5 — рефакторинг: один раз на потік, 10 ітерацій у `main`, `lock_guard`

**Зміни відносно 1.2.4:**

| Було | Стало |
|------|--------|
| Один довгий `AddToList` (10 додавань) | `AddToList(l, value)` — **одне** додавання |
| Один довгий `ListContains` (10 перевірок) | `ListContains(l, value)` — **одна** перевірка |
| `lock()` / `unlock()` | `std::lock_guard<std::mutex> guard(mtx);` у тілі функцій |
| Один запуск потоків | У `main`: цикл 10 разів — запуск потока додавання з `current`, потока перевірки з фіксованим `base`, `detach()` обох; `current++` після ітерації |

**Псевдокод `main`:**

```cpp
int base = /* з main */;
int current = base;
for (int i = 0; i < 10; ++i) {
    std::thread tAdd(AddToList, std::ref(l), current);
    std::thread tCheck(ListContains, std::ref(l), base);
    tAdd.detach();
    tCheck.detach();
    ++current;
}
// дати потокам час: join не використовується за умовою — sleep або лічильник + atomic (обговорити в звіті)
```

**Увага:** 10 пар detached-потоків без `join` — для звіту потрібна пауза в `main` (`std::this_thread::sleep_for`) або інша синхронізація, інакше `main` завершиться раніше. У звіті чесно описати обраний спосіб.

**Висновок lock_guard vs ручний lock:**

- Гарантоване звільнення при виході з функції / винятку.
- Менше ризику «забути unlock».
- Не можна вручну відпустити м’ютекс до кінця області видимості (на відміну від `unique_lock`).

### 3.6 Пункт 1.2.6 — класи `someData` та `exchangePerson`

**Клас `someData`:**

- Поля: `std::string name, surname, address;` `int age;`
- Методи: конструктор за замовчуванням, `print(std::ostream&)` або дружня функція виводу.

**Клас `exchangePerson`:**

- Приватні: `someData data;` `mutable std::mutex mtx;` (або звичайний `mutex` + const-методи обережно).
- Публічні статичні методи:
  - `static void JohnDoe(exchangePerson& obj);`
  - `static void JacobSmith(exchangePerson& obj);`
  - `static void Swap(exchangePerson& a, exchangePerson& b);`

**Заповнення (таблиця 1):**

| Поле | JohnDoe | JacobSmith |
|------|---------|------------|
| ім’я | John | Jacob |
| прізвище | Doe | Smith |
| адреса | Unknown | Known |
| вік | 120 | 1 |

**Синхронізація:**

- `JohnDoe` / `JacobSmith`: `std::lock_guard<std::mutex> lock(obj.mtx);` на час зміни полів `data`.
- `Swap`:
  1. Якщо `&a == &b` — вийти без обміну.
  2. `std::lock(a.mtx, b.mtx);`
  3. `std::lock_guard<std::mutex> la(a.mtx, std::adopt_lock);`
  4. `std::lock_guard<std::mutex> lb(b.mtx, std::adopt_lock);`
  5. Обмін `someData` (swap полів або `std::swap` для структури з оператором swap / по полях).

**`main`:**

1. `exchangePerson p1, p2;`
2. Потік 1: `JohnDoe(p1)` → `detach`
3. Потік 2: `JacobSmith(p2)` → `detach`
4. **Перед Swap:** дочекатися завершення потоків 1–2 (`join` у тимчасових `thread` або зберегти `thread` і `join`) — інакше гонка з `Swap`.
5. Потік 3: `Swap(p1, p2)` → **`join`** (вимога методички).
6. Вивести на екран (stdin/stdout за завданням — «на стандартний пристрій») поля **до** обміну (краще зняти копії або вивести після join потоків 1–2, потім викликати Swap з виводом до/після).

**Рекомендований порядок виводу для звіту:**

- Після join JohnDoe/JacobSmith — стан `p1`, `p2`.
- Після Swap — стан знову.
- Показати, що дані обмінялися між об’єктами.

### 3.7 Пункт 1.2.7 — `Swap` через `unique_lock` і `defer_lock`

**Зміни лише в `Swap` (концептуально):**

```cpp
std::unique_lock<std::mutex> la(a.mtx, std::defer_lock);
std::unique_lock<std::mutex> lb(b.mtx, std::defer_lock);
std::lock(la, lb);  // або std::lock(la.mutex(), lb.mutex()) залежно від стилю API
// далі swap даних
```

У C++17 коректний патерн:

```cpp
std::unique_lock<std::mutex> lock1(a.mtx, std::defer_lock);
std::unique_lock<std::mutex> lock2(b.mtx, std::defer_lock);
std::lock(lock1, lock2);
```

`JohnDoe` / `JacobSmith` залишити на `lock_guard`.

**Порівняння для звіту (1.2.7):**

| | `lock_guard` | `unique_lock` |
|---|--------------|----------------|
| Захоплення | Завжди в конструкторі | Можна `defer_lock`, потім `lock()` / `std::lock` |
| Володіння м’ютексом | Так | Можна `release`, переміщення |
| Накладні витрати | Менші | Більші |
| `adopt_lock` після `std::lock` | Так (як у 1.2.6) | Так само, або defer + `std::lock` на unique_lock |

---

### 3.8 Пункт 1.2.8 — висновки (зміст для звіту, без коду)

Підготувати короткий розділ:

1. **Єдиний м’ютекс на ресурс** — просто, але серіалізує доступ (список у 1.2.4–1.2.5).
2. **`std::lock` на кілька м’ютексів** — знімає deadlock при **одночасному** захопленні в правильному порядку; не допомагає, якщо різні потоки захоплюють м’ютекси в різному порядку в різний час без `std::lock`.
3. **Дисципліна порядку захоплення** — глобальний порядок `mtx1` → `mtx2` у всьому коді.
4. **`join` vs `detach`** — не про deadlock, але про коректність спостережуваних результатів.
5. **Гранулярність блокування** — великий lock (вся функція) vs малий (одна операція) — trade-off між безпекою та продуктивністю.

## 5. Ризики та типові помилки

1. **Завершення `main` до detached-потоків** — порожня консоль; вирішення: `sleep_for` або `join` там, де методичка дозволяє.
2. **UB при ітерації `list` без lock** (1.2.3) — не ігнорувати в звіті.
3. **Swap без очікування JohnDoe/JacobSmith** — обмін «порожніх» або частково заповнених даних.
4. **`&a == &b` у Swap** — обов’язкова перевірка.
5. **Два м’ютекси без `std::lock`** — можливий deadlock при розширенні коду (навчальний контраст для 1.2.6 vs 1.2.8).
